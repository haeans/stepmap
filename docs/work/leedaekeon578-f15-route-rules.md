### 계획 (처음 계획 1~7)

지도 범위에서 먼 공항 빼기는 결정 2에, 호출 수 제한·캐시·실패 처리는 결정 1에 있어 여기에는 넣지 않는다.

1. **이름에서 출발지·도착지 뽑기**: 새로 만들지 않고 `route-name.ts`의 `splitRoute`로 대신한다(결정 3).
2. **거점 검색어**: 비행기는 "○○ 공항", 그 밖은 "○○ 역", 버스는 "○○ 터미널"로 만든다. 이미 공항·역·터미널로 끝나면 덧붙이지 않는다. 도시 이름만 나오는 결과(지역 결과)는 버린다(기존 `isAreaResult` 재사용). 짧은 출발지·도착지는 거점을 찾지 않는다(결정 3).
3. **일차별 동선**(결정 4)
   - 시작: 그날 도착하는 교통의 도착 거점. 없으면 전날 숙소
   - 중간: 장소와 교통 항목을 시각 순서로 놓는다
   - 끝: 그날 밤 숙소. 떠나는 날이면 출발 거점
4. **경로 구하기**: 교통 구간은 Routes API를 부르지 않는다. 땅 위 구간끼리만 지금의 `dayRoute`로 구한다.
5. **선 모양 셋**(`route-map.tsx`, 결정 6): 실제 경로는 실선, 비행기·교통 구간은 둥근 점선이다. 경로를 못 찾은 구간은 지금처럼 대시다. 비행기 구간 선 위에 ✈를 얹지 않는다.
6. **공항 ✈ 표시와 패널 구간 표시**(`route-map.tsx`, `map-view.tsx`, 결정 5·6): 공항 거점에만 지도에 ✈ 표시를 그린다(도착하는 날의 시작 공항, 떠나는 날의 끝 공항 둘 다). 기차역·터미널 거점과 전날 숙소는 표시 없이 동선의 점으로만 쓴다. 표시는 누르는 기능이 없다. 패널의 구간 표시에는 "비행기"·"교통"을 쓴다.
7. **자체검수**: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`, 회귀 항목 확인 → PR 본문에 `Closes #35`.

## 2. 완료 기준

- [ ] 이름에 출발·도착이 있는 교통 항목(예: `KE123 ICN → KIX`, `KE123 인천→홍콩`, `KTX 101 서울→부산`)은 그날 동선에 출발 거점과 도착 거점이 들어간다
- [ ] 출발지·도착지가 영문·숫자로만 된 2자 이하(예: `T1`, `A`)이거나 교통 패스이면, 그쪽 거점 없이 지금처럼 그린다. 한글 2자(인천·서울)와 3자 공항 코드는 거점을 찾는다 (결정 3)
- [ ] 그날 동선의 시작은 그날 도착하는 교통의 도착 거점(없으면 전날 숙소)이고, 끝은 그날 밤 숙소(떠나는 날이면 출발 거점)다 (결정 4)
- [ ] 선 모양이 셋으로 나뉜다: 실제 경로는 실선, 비행기·교통 구간은 둥근 점선, 경로를 못 찾은 구간은 대시. 비행기 구간 선 위에는 ✈를 얹지 않는다 (결정 6)
- [ ] 공항 거점에만 지도에 ✈ 표시가 그려진다. 도착하는 날의 시작 공항과 떠나는 날의 끝 공항 둘 다 그렇다. 기차역·터미널 거점과 전날 숙소에는 표시가 없고 선의 점으로만 쓰인다. ✈ 표시는 눌러도 아무 일이 없다. 패널 장소 목록과 번호는 그대로다 (결정 5)
- [ ] 패널의 구간 표시에 "비행기"·"교통"이 보인다 (결정 6)
- [ ] PC에서 패널을 접은 채 지도의 핀을 누르면 패널이 펼쳐지고 그 장소의 세부(이름·종류·시각·주소·메모·비용·링크)가 패널 아래 카드에 보인다. 이미 고른 핀을 접힌 채로 다시 눌러도 펼쳐진다. 펼친 뒤 고른 핀이 패널에 가리지 않는다 (결정 7)
- [ ] 모바일에서 핀을 누르면 시트가 펼쳐지는 동작은 그대로다 (결정 7)
- [ ] 비행기 구간이 다른 나라까지 이어지는 날, 지도 범위는 그날 장소(거점 포함, 멀리 떨어진 반대편 공항 제외)에 맞춰지고 점선은 화면 밖으로 이어진다 (결정 2)
- [ ] 여행 하나를 처음 열 때 거점 찾기 호출이 최대 40번이고, 다시 열면 0번이다 (결정 1)
- [ ] 거점을 못 찾거나 호출이 실패한 교통 항목은 지금처럼(거점 없이) 그려지고 지도 화면이 깨지지 않는다
- [ ] 기존 지도 기능 유지: F14 완료 기준 전부, 일차별 색 번호 핀, 실제 경로 선, 구간 거리·이동 수단, `regression.md` R-06·R-07
- [ ] `npm run lint`, `npm run typecheck`, `npm test`, `npm run build` 통과

| [leedaekeon578-f15-route-rules] 결정 1 | 지도 | (F14 작업 파일 결정 1을 옮김) 교통 거점 좌표는 DB에 저장하지 않고 지도를 그릴 때 서버에서 찾는다. B11의 예정 메모("교통 항목도 도착지 좌표를 찾음")와 다르다. 칸이 `lat/lng` 하나뿐이라 출발지를 담을 수 없어 떠나는 날 동선의 끝(출발 공항·역)을 그릴 수 없기 때문이다. 이렇게 하면 DB 변경이 없고, 이미 저장된 여행에도 바로 적용되며, 항목 저장(`store.ts`)을 고치지 않아 F18·F19와 겹치지 않는다. **호출 수**: 교통 항목마다 출발·도착 검색어 2개를 만들고, 검색어마다 Places Text Search를 최대 1번 부른다(다시 시도하지 않음). 한 여행 안에서 같은 검색어는 한 번만 부른다(예: 가는 편 `ICN→KIX`와 오는 편 `KIX→ICN`은 2번). 교통 항목은 일정 순서로 앞 20개까지만 거점을 찾는다. 그래서 **여행 하나를 처음 열 때 최대 40번**이고, 캐시가 살아 있는 동안 다시 열면 0번이다. 21번째 교통 항목부터는 거점 없이 지금처럼 그린다. **캐시**: 경로 캐시(B21)와 같은 Next.js `unstable_cache`를 쓰고, 키는 `["hub-geocode-v1", 검색어]`, 보관은 30일이다. 키에 여행 id를 넣지 않으므로 여러 여행이 캐시를 함께 쓴다("인천 공항"은 한 번만 찾음). 찾는 결과가 없는 것(null)도 캐시해 같은 검색어를 다시 부르지 않는다. 호출이 실패하면(시간 초과·4xx·5xx) 캐시하지 않고 그 구간만 거점 없이 그린 뒤 다음에 열 때 다시 시도한다. 교통 항목 이름을 고치면 검색어가 바뀌어 새로 찾는다. |

"공항"·"airport"는 비행기 판정 말에 넣지 않는다(공항철도·Airport Express는 기차). `go-info.ts`는 고치지 않았다. |

- `splitRoute`(`route-name.ts`, F17)와 `parseRide`(`go-info.ts`, F16)가 같은 교통 이름을 서로 다르게 나눈다. 다른 점: 도착지 뒤 낱말 처리(`동서울 -> 속초 고속버스` → `속초 고속버스` / `속초`), 화살표 종류(`parseRide`는 `⇒ ~ >`도 읽음). 지금은 입력창과 매거진 GO 패널이 같은 이름을 다르게 볼 수 있다. F15는 두 파일을 고치지 않는다. 나중에 하나로 합칠지는 팀이 정한다.
