# 04-DB

테이블과 관계, 카테고리·세부 필드 정의, 권한 규칙, 스키마를 정하는 문서입니다.

> 작성: AI · 갱신: 사이클마다 · 현재는 개념 수준이다. 테이블 이름·필드 형식·스키마는 사이클별 계획 단계에서 채운다.

## 1. 데이터 (개념)

### 사용자

Supabase Auth가 관리한다.

- 구글 계정 식별값
- 이메일
- 이름

### 여행

- 소유자
- 제목 (예: 홍콩 3박 4일)
- 목적지
- 시작일·종료일
- 동행 인원 (정산용)
- 대표 이미지 (주소, 대표 색, 출처, 작가 이름·링크) (C7)
- 만든 시각
- 고친 시각

### 일정 항목

- 소속 여행
- 일차
- 시각
- 같은 날 안의 순서
- 종류
- 이름
- 주소·좌표
- 메모
- 링크
- 비용: 금액·통화 (선택 입력)
- 입력 방식: 직접 / AI
- 장소 사진: Google 장소 ID, Wikimedia 사진 주소·출처 (C8)

### 예약 정보 (C8)

- 대상 일정 항목 (항목마다 0~1개)
- 예약번호
- 예약 링크
- 공개 단계: 소유자만 / 비밀(주소를 보여 주지 않음)
- 소유자만 읽고 쓴다. 공유받은 사람과 AI에는 보내지 않는다(B121).

### 공유 링크

- 대상 여행
- 링크 식별값 (추측하기 어려운 값)
- 만든 시각

### 공유받은 사람

- 대상 여행
- 사용자
- 권한 (v1.0은 보기 전용 하나)
- 받은 시각

## 2. 관계

- 사용자 1 — N 여행 (소유자)
- 여행 1 — N 일정 항목
- 일정 항목 1 — 0..1 예약 정보 (C8 F20, 항목·여행을 지우면 함께 지운다)
- 여행 1 — N 공유 링크
- 여행 1 — N 공유받은 사람, 사용자 1 — N 공유받은 사람
- 여행 1 — 0..1 올린 대표 이미지 파일 (Storage `trip-covers/<여행 id>/cover`, C7)
- 여행을 지우면 그 여행의 항목과 공유 정보도 함께 지운다. 올린 대표 이미지 파일은 DB가 아니라 앱(`deleteTrip`)이 지운다(B54).

## 3. 항목 종류 (카테고리)

교통 · 숙소 · 관광지 · 식당 · 메모 (5종)

그 외 종류는 확장 단계에서 다룬다.

## 4. 정렬 기준

지도 동선은 **일차 → 시각 → 순서** 기준으로 이어 그린다.

## 5. 비용 계산 (R-09)

- 항목의 비용(금액·통화)을 **통화별로 따로** 합계 낸다. 환율 계산은 하지 않는다.
- 통화별 1인당 금액 = 통화별 총액 ÷ 여행의 동행 인원
- 항목을 고치거나 지우면 결과도 바로 바뀐다.

## 6. 원문 처리

- 붙여넣은 원문은 저장하지 않고 추출 결과만 저장한다.
- 이유: 예약번호 같은 개인정보가 남는 것을 줄이기 위해서다.
- "다시 추출하기"는 하지 않는다.

## 7. 권한 규칙 (Supabase RLS)

| 대상 | 만들기·고치기·지우기 | 보기 |
|---|---|---|
| 여행 | 소유자만 | 소유자, 공유받은 사람 |
| 일정 항목 | 소유자만 | 소유자, 공유받은 사람 |
| 예약 정보 (C8 F20) | 소유자만 | 소유자만 |
| 공유 링크 | 소유자만 | 소유자 |
| 올린 대표 이미지 (Storage, C7) | 소유자만 | 공개 주소를 아는 누구나 |

- 공유 링크로 들어와 로그인하면 "공유받은 사람"으로 등록된다.
- 여행을 지우면 그 여행의 항목과 공유 정보도 함께 지운다.
- RLS 정책 정의는 Drizzle로 한다. 데이터 읽기·쓰기는 로그인 사용자 권한의 Supabase 클라이언트로 한다.
- Supabase 프로젝트 설정(B6): Data API 켬, 새 테이블 자동 공개 끔, 자동 RLS 켬.
  - 테이블마다 마이그레이션에서 `authenticated` 역할에만 필요한 권한(`GRANT`)을 준다. `anon` 역할에는 주지 않는다.
  - 자동 공개를 꺼도 Supabase 기본 권한으로 TRUNCATE·REFERENCES·TRIGGER가 남는다. TRUNCATE는 RLS를 거치지 않으므로 테이블마다 회수한다(B8).

## 8. 스키마

정의는 `src/db/schema.ts`, 마이그레이션은 `drizzle/`에 있다. 테이블을 추가할 때는 아래 순서를 따른다.

1. `schema.ts`에 테이블과 `pgPolicy`를 쓴다.
2. `npm run db:generate`로 마이그레이션을 만든다.
3. `npx drizzle-kit generate --custom --name <이름>`으로 빈 파일을 만들고 GRANT, REVOKE, 트리거를 직접 쓴다.
4. `npm run db:migrate`로 적용한다. `DATABASE_URL`은 Session pooler 주소다(Direct connection은 IPv6 전용).

| 컬럼 | 형식 | 기본값 | 제약 |
|---|---|---|---|
| `trip_id` | uuid | | `trips(id)` 참조, 여행 삭제 시 함께 삭제 |

### accept_share(share_token text) → uuid (v0.9)

- SECURITY DEFINER, `search_path = ''`. `authenticated`만 실행할 수 있다(`anon`, PUBLIC 회수).
- 식별값이 맞으면 로그인한 본인을 `viewer`로 넣고(이미 있으면 그대로) 여행 id를 돌려준다. 소유자 본인이면 넣지 않는다. 틀리면 null.
- 공유받은 사람 표의 보기 정책은 본인 행만 보므로, `trips` 보기 정책이 이 표를 참조해도 서로 물고 들어가지 않는다.

### Storage 버킷 `trip-covers` (C7, 0008)

- 직접 쓴 마이그레이션 `drizzle/0008_trip_covers_storage.sql`이 만든다. 공개 버킷, 5MB 이하, `image/jpeg`·`image/png`·`image/webp`만.
- 파일은 여행마다 `<여행 id>/cover` 하나(B51). 공개 주소로 보는 것은 정책과 상관없다(주소에 무작위 여행 id가 들어간다).

| 정책 (`storage.objects`) | 대상 | 조건 |
|---|---|---|
| `trip_covers_select_owner` | select | `bucket_id = 'trip-covers'` 그리고 `owns_trip_cover(name)` |
| `trip_covers_insert_owner` | insert | 같음 |
| `trip_covers_update_owner` | update | 같음 (고친 뒤에도) |
| `trip_covers_delete_owner` | delete | 같음 |

- `owns_trip_cover(object_name text) → boolean`: 이름이 `<uuid>/cover` 모양이고 그 여행의 `owner_id = auth.uid()`이면 참. SECURITY INVOKER(기본값), `search_path = ''`. `PUBLIC`·`anon`에서 실행 권한을 회수하고 `authenticated`에만 준다.
- 덮어쓰기(upsert)에는 보기·넣기·고치기 정책이 모두 필요하다.
